## 1. 서비스 배경

**SJ Hub**는 3단 유통·판매·정산 플랫폼이다.

- **CA (운영사 어드민)**: SJ Hub 본사. 전체 조직·대리점·정산을 관리하는 최상위 어드민. 조직 관리 + 일정산 집행이 핵심. 은행 미연동 — 시스템 밖에서 송금 후 정산 상태를 수동 변경.
- **SA (영업조직 어드민)**: 지사(1단계) → 총판(2단계) → 영업(3단계) 위계의 영업조직이 사용. "받을 정산금 / 하위에 내려줄 정산금 확인"이 목적. 조회 중심.
- **BA (대리점 어드민, 제품명 link it)**: 대리점(=브랜드=파트너사=가맹점, 모두 동일 주체)이 상품·상점·주문·배송을 실제 운영.
- 대리점은 지사/총판/영업 어느 단계에서든, 또는 CA와 직접 연결될 수 있음 (신청 출처 5분류: CA 직접 등록 / 지사 등록 / 총판 등록 / 영업 등록 / 대리점 직접 신청).
- 셀러: 대리점이 BA에서 등록하는 하위 판매 계정. 별도 셀러 어드민 존재. 현 개편에서 비중 낮음.

## 3. 버전 이력 (모두 settlement-v2.js에 구현됨)

### v2 — 데이터 구조 이슈 17건 개선 (S-01~S-17)
원본 분석에서 발견한 이슈. 핵심: 단일 원천 데이터 파생(KPI 하드코딩 제거), (대상×회차) 정산 로우,
차등(포함형) 수수료 분배, 취소 반영 공식 통일, parentId FK + 위계 검증(지사→총판→영업),
상태 전이표(필요→대기→중→완료, 완료 취소는 사유 필수 + 이력), 용어 단일화.

### v2.1 — 유보금·예치금 개편 (운영 정책)
운영 어드민에서 상점관리 팝업에 있던 유보금/예치금을 **정산관리의 탭 화면(ca-022)**으로 이동.
- 목적 동일: 정산 완료 후 결제 취소 발생 대비금.
- **유보금**: 결제마다 비율 자동 적립 — 수동 등록 버튼 없음. '사용' 버튼만(사유 필수).
  한도 도달 시 적립 중단 + **인출 알림**(배너/뱃지) + 인출 처리 액션.
  **90일+ 무사고 보유 시 '사용등록' 기록** 액션(관리자가 시점·메모 기록).
- **예치금**: 미리 받아두는 대비금. 등록/차감 수동, 사유 필수, 잔액 검증.
- 행 삭제 금지 → **역분개(정정)** 방식. 자동 적립 건은 수정 불가.

### v2.2 — 정산 방향·주기·취소 정책 (담당자 피드백 2026-07-15)
- **결제금액(원금) 기준.** 대리점 수수료 = 운영사가 떼는 몫.
  → 대리점 지급 = 결제원금 − 수수료 − 유보금.
- **유보금 = 결제 원금 × 유보율**, 한도까지 계속 차감.
- **조직 수수료는 수수료 풀 안에서 지급**: 남은 수수료로 조직 차등 지급, 잔여 = CA 마진.
  검증: 체인 최상위 조직율 ≤ 대리점 수수료율. (분배 보기 모달 = 결제원금 100% 분해)
- **전역 회차(일/주/월) 폐지 → 정산 기준일 + 대상별 주기(D+N일)**.
  오늘 정산 매출 = 각 대상의 주기만큼 이전에 결제된 매출 (`paidDate == 기준일 − cycleDays`).
- **취소**: 기준일에 확정된 취소(이전 결제분)를 매출에서 차감 — 대리점·조직 동일.
  차감 > 매출이면 음수 표시 + "익일 이월" 경고 (실제 이월 로직은 미구현 — 정책 미정).
- **당일 주문 + 당일 취소는 모든 계산에서 제외** (`isSameDayCancel`).

### v2.3 — 4개 정산 페이지 컬럼 개편 (클라이언트 요청, 원문 중국어)
지사·총판·영업·대리점 페이지 공통:
1. '정산 금액(结算金额)' 컬럼명 → **'수수료(手续费)'**
2. **'정산 예정 금액(应结算金额)'** 신설 = 매출 − 수수료
3. **'정산 상태(结算状态)' 컬럼 삭제** — 보이지 않는 상태 기준 검색을 피하기 위해 상태 필터도 삭제. 단, 상태 워크플로우(변경/지급완료)는 유지,
   개별 상태는 상세 화면의 "기준일 상태" 배너에서 확인.

### v2.4 — 테이블 데이터·공식 확정 (클라이언트 레퍼런스 테이블)
클라이언트가 지사(分公司) 페이지 레퍼런스 테이블(10행, 원 단위 수치)을 제공 → 데이터 레이어 재구성.
- 4페이지 공통 컬럼: 명칭 | (소속/출처) | 수수료율 | 총 판매금액 | 정산 건수 | 수수료 | 정산 예정 금액 | 상세
- **공식 확정: 수수료 = round(총판매금액 × 수수료율) · 정산 예정 금액 = 총판매금액 − 수수료**
- 각 레벨 수수료 **독립 계산** (v2의 차등 분배 모델 폐기 — 클라이언트 수치로 확정됨)
- 데이터: 지사 = 레퍼런스 10행 그대로 (100,000/17건/7% …). 총판·영업·대리점 = 운영 스크린샷
  시리즈 (sales = 80,000 + i×43,120 · count = 8 + i×3 · fee 사이클: 총판 6,7,8,5… 영업 5,6,7,4… 대리점 7,8,9,6…)
- 상세 내역은 목록 집계와 정확히 일치하게 분해 생성 (`makeDetailRows`: 판매금액 합 = 총판매금액,
  수수료 합 = 수수료, 행 수 = 정산 건수, 마지막 행이 반올림 흡수)
- v2.2의 주기(D+N)·취소 차감 컬럼은 목록에서 제거 (레퍼런스 레이아웃 준수). 기준일 패널은
  상태 기록 단위로만 유지. 유보금 차감은 목록 미표시 — 유보금·예치금 관리에서 처리, ⚠/⏱ 뱃지로 연결
- v2.3의 열린 질문(조직 페이지 정산 예정 금액 의미) → **매출 − 수수료로 확정, 해소**

### v2.5 — KPI 6종 카드 + 상태 관리를 상세 페이지로 이동 ★현재
- **KPI 6종 카드** (4개 목록 + 상세 공통): 총 정산 수 / 정산 완료 건 / 정산 필요 건 /
  정산 총액 / 정산 완료 금액 / 정산 필요 금액 — 전부 **거래(건) 단위** 집계라 목록·상세 항상 일치.
  금액 기준 = 지불해야 할 정산 금액(settle). 필요 = 완료가 아닌 모든 상태.
- **목록 테이블 = 스펙 컬럼만**: 명칭 - (소속/출처) - 수수료율 - 총 판매금액 - 정산 건수 -
  수수료 - **지불해야 할 정산 금액** - 상세내역. 체크박스·상태 컬럼·상태 필터·일괄 버튼 제거.
- **정산 상태·상태 변경·상태별 필터는 상세 페이지(ca-014)로 이동**: 거래 행마다 상태 뱃지,
  체크박스 + 전체 선택 + 선택항목 상태 변경(전이표 강제) + 지급완료(정산중만) + 상태 필터.
- 상태 저장: `txStatusStore[ownerId] = 상태배열` (상세 행 인덱스 정렬, `getTxStatuses`).
  시드: `_01` 대상은 전건 '정산 완료'(지사_01 = 17건/93,000원 완료 데모), 나머지는 5종 순환.
- `statusStore`(대상×기준일 단위) 제거 — 상태는 거래 단위로 일원화.
- **상태 3단계로 단순화**: 정산 필요 → 정산중 → 정산 완료. 색상 구분 뱃지(`.v2-st--need` 빨강 /
  `.v2-st--ing` 주황 / `.v2-st--done` 초록, settlement-v2.css). 전이: 필요→중, 중→완료|필요(되돌리기),
  완료→중(완료 취소, 사유 필수). '정산대기'·'정산 보류' 상태 폐기.

### v2.5 — KPI 6카드 및 중국어 번역 보정
지사·총판·영업·대리점 목록 상단 KPI를 **총 정산 수 / 정산 완료 건 / 정산 필요 건 / 정산 총액 / 정산 완료 금액 / 정산 필요 금액** 6개 카드로 통일.
금액 KPI는 클라이언트 피드백 기준의 **应结算金额 = 总销售金额 − 手续费**(`payable`) 합계로 계산한다.
중국어 사전 보정: `수수료 → 手续费`, `정산 예정 금액 → 应结算金额`, `정산 총액 → 应结算总额`, `총 정산 수 → 总结算件数`.

### v2.6 — 의미 없는 상태 필터 제거 ★현재
목록 테이블에서 `结算状态` 컬럼을 삭제한 뒤, 보이지 않는 상태값으로 검색하는 `정산상태 전체` 필터가 혼동을 만들어 제거.
상태 데이터는 KPI(정산 완료/필요)와 상태 변경·지급완료 워크플로우를 위해 내부적으로만 유지한다.

## 4. 데이터 모델 (v2.4 기준 — settlement-v2.js 내 mock)

```
BRANCHES / DISTS / SALESREPS / BRANDS   // 페이지별 집계 로우 (고정 데모 값)
  { id, name, fee(%), sales(총판매금액), count(정산 건수),
    parentName·grandName(조직 소속) | source·managerName(대리점) }
RETENTION_CONF { brandId(bd01~bd10): { rate(%), limit(원) } }
RET_LOGS / DEP_LOGS { brandId: [{at, type, amount, reason, by}] }  // 수동 이벤트 원장
statusStore { "type|id|run|기준일": { status, history[] } }        // 기준일별 상태
```

핵심 함수:
- `fee(sales, rate)` = round(sales × rate / 100) — 수수료
- `toRow(src, type, ck)` — 목록 로우: payable = sales − fee ← **확정 공식**
- `makeDetailRows(owner, type)` — 상세 분해: count건 거래, 판매금액 합 = sales,
  수수료 합 = fee (마지막 행이 반올림 흡수) → 목록·상세 항상 일치
- `dailyBases(brand)` — 총판매금액을 7일로 분해 (유보 적립 산출용)
- `retentionLedger(brandId)` — 일별 자동 적립(일매출×유보율, 한도 캡) + 수동 이벤트 재생
- `retentionStatus(brandId)` — {balance, overLimit(한도 도달), needUseReg(90일+), heldDays…}

상태 전이표: 필요→[대기,보류] / 대기→[중,보류] / 중→[완료,보류] / 완료→[중(=완료 취소, 사유 필수)] / 보류→[필요].
지급완료는 '정산중' 상태만, 기준일 단위로만 기록.

데모 케이스: 대리점_09 = 유보 한도(30,000원) 도달 → ⚠인출 필요 / 대리점_03 = 3/15 이월 적립 → ⏱90일+ 사용등록 필요.
